# Releases: the lock, the shells and the order

**For**: whoever releases an addon, a game or the web shell. **Quick start** (an addon):

```bash
git -C ../gs-vote tag v0.2.1 && git -C ../gs-vote push origin v0.2.1   # 1. tag the addon
tools/addons-lock.sh write                                               # 2. lock it here (check the pack is on the origin first)
git add addons.lock && git commit -m "Lock gs-vote v0.2.1" && git push  # 3. free: CI and the dev channel run; nothing is released
```

**Pushing to `main` releases nothing** ([main is free](#main-is-free-releases-are-batched)). **Never** export, upload or pin a web shell by hand while the workflow is up; the order for a game is in the table below.

## A game pack against the lock

A game pack's `requires.json` is capped at the levels the shell's lock pins, and a `requires.floor.json` level above them stops `publish_pack.sh`, since players' shells would refuse the pack. `tools/pack_ready.sh <game-dir>` judges every floor against **origin/main's** `addons.lock` (not the checkout's) and names one state per floor:

| State | Meaning | What moves it |
| --- | --- | --- |
| OK | floor ≤ the lock's level | nothing |
| LOCKABLE | the addon's newest tag reaches it (also: the locked tag predates the addon's rename) | the lock bump `--prepare` pushes |
| NEEDS_TAG | only the addon's origin/main reaches it | the printed `git tag` + push (supervisor), then the lock bump |
| WRONG | no commit has the level | lower the floor in the game |
| STALE | the lock carries no such addon, so the host never checks it | remove the floor from the game |

`--prepare` commits the lock line and the `content-lists/addons.yml` pin for each LOCKABLE/NEEDS_TAG repository on a worktree branch `lockbump/<game>-<stamp>` off origin/main, pushes the branch, and prints the steps in order: tags, fast-forward main, the shell (the web-shell workflow, else `tools/publish-web-shell.sh`), then rerun. Exit 0 = publishable, 1 = actions printed, 2 = usage or git failure. Test: `tools/test_pack_ready.sh`.


This repository is where an addon release, a game release and a shell release meet. The family's release checklist is in the `release-rules` memory; this is what the code here enforces and why.

## Publish gates (no override)

Born of the 2026-11-22 prod solo outage (the rename changed the manifest marker against manifests already published) and of v0.1.150 being tagged over a failing `check-pins`. Each is mechanical; a red one is fixed at its cause, never bypassed.

- **`release.yml`** has an `addon-pins` job (`addons-lock.sh check-pins`) the release job needs; `ci.yml` runs the same.
- **`tools/publish_gate.sh`** runs first in `publish-native-shell.sh`, `publish-web-shell.sh` (not for `--dry-run` / `--manifest-only`) and as a step of `native-shell.yml` / `web-shell.yml`. It refuses an unpinned lock, a missing or `-dirty` `client/build_stamp.gd`, and a locked addon tag whose own CI (GitHub check runs of the tag's commit, `addons-lock.sh check-ci`) is red, unfinished or absent. Offline proof: `tools/check_publish_gate.sh`.
- **`tools/check_solo_smoke.sh`** (with `tools/solo_manifest_probe.gd`) resolves `latest.json` and the signed manifest of at least 3 games from `GS_CONTENT_ORIGIN` and has the shipped gs-cloud client parse and verify them. The shell workflows run it before publishing against `vars.SOLO_SMOKE_ORIGIN` (default prod, `https://content.gamespice.net/content`); run it against dev (`https://tmcdevgames.net/content`) first. `GS_SMOKE_STRICT_MARKER=1` also fails a manifest still on the legacy `dot_cloud_signed` marker: turn it on once prod is re-signed and the alias is removed.
- **`tools/verify-prod-solo.sh`** is the read-only end-to-end proof, run against dev first and prod after a shell or content publish: `tools/verify-prod-solo.sh [--origin URL] [--games a,b,c] [--native] [--web] --bin <desktop export> [--browser]`. It reuses `check_solo_smoke.sh` for the manifests (legacy `dot_cloud_signed` and `gs_cloud_signed` both), then starts the shipped native shell headless with `--solo owner/game --content-url <origin>/content` twice per game (default fatal-contact, playlot, zombie-zone, prop-hunt, murder-mystery) and fails, naming the game, when: the log says "Could not download the content manifest", "solo game started" never appears, or the second launch on the same cache downloads any object (workshop lines excepted). `--web` checks the shell pointer and entry of the web build and, with `--browser` (GPU box), opens `embed.html?solo=gamemann/game-airdrift`. It only GETs and never touches a token. Offline test: `tests/test_verify_prod_solo.sh` (canned logs plus a saved real prod manifest under the legacy marker, `tests/fixtures/`).
- **The published-artifact gate** (born of the 2026-11-23 prod Fatal Contact outage: the published shell carried both `dot_*` and `gs_*` addons, `dot_combat/dot_pellet_tracer.gd` and `gs_combat/gs_pellet_tracer.gd` both owned `uid://cbebxr4alar6d`, and servers would not boot; every test had run the repo tree, which never had both). It judges the EXACT built artifact, never the source tree:
  - **`tools/check_artifact_static.sh INPUT...`** (Godot reads the pck via `tools/artifact_unpack.gd`; `tools/check_artifact_static.py` judges). Inputs are a shell `.pck`, a native `.zip`, or a directory (an install tree, or a pack from gs-cloud's `pack_fetch.py`); all of them are ONE `res://` namespace, so list the shell then a pack to catch a clash between the two. Fails on any `addons/dot_*` dir or `dot_*.gd`, any `Dot*` class, any `uid://` claimed by two files. `publish-web-shell.sh` runs it on the zip's `index.pck`, `publish-native-shell.sh` on `tmc-linux-x64.zip`, and a red one refuses the publish; `native-shell.yml` and `web-shell.yml` run it as the "Artifact gate" step before the publish gate.
  - **`tools/artifact_boot_smoke.sh [--tree DIR] [--origin URL] [--only ids]`** starts a headless dedicated server the way prod does (`./server --port P --game ID --games OWNER/ID --content-url ORIGIN`, `TMC_AUTO_UPDATE=never` so the tree is what is tested) once per game in `content-lists/games.yml` (the shell workflows boot `game-fatal-contact`), and FAILS on a log line matching `ERROR:`, `SCRIPT ERROR`, `would not load`, `Cannot convert argument`, `must extend` or `crashed state`, on a game that never logs `content ready` and `module loaded for the current game`, or when `tools/a2s_probe.py` (A2S_INFO over UDP, what a browser asks) gets no answer. Run it through `hv`; point `--tree` at a prod-shaped install (a stale tree upgraded in place shows what a new install hides) and `--origin` at the dev origin (`https://tmcdevgames.net/content`) to try a pack before it is published.
  - **`tools/published_artifact_nightly.sh`** fetches the CURRENTLY PUBLISHED prod web shell (`godot/latest.json` to `embed.html` to the engine pck), runs the static check on it and the boot smoke on every published game. `.github/workflows/published-artifact-nightly.yml` runs it at 03:37 UTC; on the dev box the fleet watchdog runs it and a red night becomes a note on the board item `published-artifact-drift`.
  - Test: `tests/test_artifact_static.sh` (fixtures with a duplicate uid, a `dot_*` dir, a shell/pack clash; part of `tools/check.sh`).
- **`tools/release-shell.sh web|native [--dry-run]`** is the whole release from our own boxes (GitHub quota exhaustion stalled releases, and the risk is in build and verify, not the upload). Run it as `gamedev` in a lock-exact checkout (`./setup.sh --no-games`). Order, every step fatal, no override: (1) refuse a dirty tracked tree, a checkout behind `origin/main`, a failing `check-pins`, addons off `addons.lock`; (2) addon CI per locked tag read from the internal Forgejo first (`gs-bootstrap/tools/ci-red-forgejo.sh`; red, cancelled or running refuses), and only repos Forgejo has no run for fall to GitHub through `addons-lock.sh check-ci` with a private copy of its cache (`tools/gh-quota.sh need N` first when that tool exists); (3) build the export through `hv` (else this VM through `heavy`) and record its inputs; (4) `publish_gate.sh` (so a `-dirty` stamp refuses), `check_solo_smoke.sh` against the dev origin (`--dev-key` for the tmc-dev key), then a read-only prod check: `tools/verify-prod-solo.sh` when it exists (second launch makes zero downloads), else `check_solo_smoke.sh` on the prod origin; (5) the tree is re-fingerprinted against the export, then `publish-web-shell.sh --pin` (upload, pin, tag; its own shell-inputs compare is the check `release.yml` runs) or `publish-native-shell.sh` (native has no pin or tag). `--dry-run` stops before any upload or tag. The prod creator token is read from `SHELL_PUBLISH_TOKEN` or `--env FILE` and never printed. `web-shell.yml` and `native-shell.yml` are unchanged for now; GitHub only needs to run CI on the tag once they are cut over. Offline proof: `tools/check_release_shell.sh`.

## The release orders

| Releasing | Order |
| --- | --- |
| an addon | tag the addon → the site publishes its pack (hourly, or "Pull now") → bump `addons.lock` here (`tools/addons-lock.sh write`) and push → restart the servers |
| a game | tag every addon it needs → lock them here and push → the next batched release (`tools/release.sh`) pins the shell and tags → tag the game |
| a new shell | `tools/release-shell.sh web` (builds, verifies, uploads, pins, tags), or `tools/release.sh` then the `web-shell.yml` dispatch with the candidate ([below](#publishing-the-web-build)) |

- **Push the lock only after the packs are on the origin.** A client that cannot fetch an addon pack joins on its own addons and does not retry that server this session. Check with `curl <origin>/<owner>/<repo>/<version>/manifest.json`.
- **Each skipped step in the game order fails in CI**, not on a box: this repository's CI parses every script against `addons.lock` at the locked refs (gs-ci resolves a project that has a lock from the lock), and a game's release refuses a pack no released gs-server-deploy can run (gs-ci `scripts/server-compat.sh`).
- **Publish content before the build that needs it.** A build published without its packs is a client that can mount no game; in the other order every player on the new build is briefly on a client that can reach nothing.

## What needs a new shell

An addon release reaches players by a server restart ([addon-packs.md](addon-packs.md)). A new shell (web and native) is still needed for:

- the engine version;
- the boot stage (`client/boot.tscn`, GameSpice Cloud's `gs_cloud_boot.gd`);
- the shell's own `client/` code (the admin menu, loading screen, notice overlay, party and friends UI);
- a GameSpice Server signon revision change (an older shell is refused with "This server needs a different build of the game client");
- an addon release that adds or changes files outside its own `addons/<dir>/` (the weapons pack's art is in `res://assets/`).
- a change to the page the engine runs in (`web/embed.html`, or an addon's page script such as gs-audio's `web/gs_audio_ceiling.js`, which `export-web` copies beside the build): an overlay lays files under `res://`, never next to `index.html`.

An older shell ignores notice topics and `data` it does not know, so a server ahead of the shell degrades rather than breaks for the HUD features; the signon revision is the hard line.

## `addons.lock`

`addons.lock` names a ref (a release tag) per addon repository. `setup.sh` clones at it and moves its own clones there on `--update`, which the egg passes on every reinstall. Before the lock, every install took each addon's `main` on the day while the shells were exported whenever, and a server ahead of the shell refused the join.

- **Only what `setup.sh` owns is ever moved**: a fresh clone, or a clone under `addons/.repos/`. A developer's sibling checkout or a shared `--addons-dir` is never detached onto a tag. On a developer box the lock is a statement, not an action.
- **`tools/addons-lock.sh check` before `./server export-web` or `export-native`**: a shell exported from a tree that is not at the lock is a shell no locked server matches. Check against the tags, not only the sibling checkouts, which are usually ahead.
- `tools/addons-lock.sh write` re-locks every repository to its newest `v*` tag (by `sort -V`, not by date), `write v0.1.3` to one tag, and **refuses to write a lock with a hole in it**: a missing entry would install that addon at `main`. `TMC_ADDONS_LOCK=off` restores the old behaviour.
- **Compare commits, not tag names.** A tag can be re-pointed after it is cut, and an annotated tag lists twice in `ls-remote` (the tag object, then `^{}`), so `check` peels to the commit.

## A game that needs newer addons

A box's addons used to move only when somebody reinstalled, so a game released against a newer addon API level installed on restart and then refused to boot.

- **`install-games` will not install a pack the addons cannot run** and exits 4 (`EXIT_ADDONS_BEHIND`) ([installing-games.md](installing-games.md#rules-of-the-installer)).
- **A kept version must still mount.** When the newest pack needs newer addons, the installed version is kept, but one signed before the site stamped `provides.runs_code` (website-city 3e0fa9487, 2026-11-13) and shipping code is refused at mount ("The pack's files run code its manifest did not declare"). `install-games` checks the kept version's manifest (`refused_at_mount`), logs an error with the fix, and prints `UNUSABLE` instead of a quiet "kept". Found on a panel box whose addons stayed at the 2026-11-13 lock with Prop Hunt 0.1.15 as its fallback.
- **An older game than asked for is an ERROR, at install and at load** (2026-11-16). The installer logs it at ERROR and records it in `data/installed-games.json` as `behind: {<content id>: {wanted, why}}` (rewritten every run); the launcher prints `ERROR:` (red) when the update did not fix it; and when that game loads, the host logs "this game is OLDER than the server list asks for" with the running and wanted versions and the fix (Reinstall). A Zombie Zone box ran 0.1.9 with no maps for days behind a yellow warning.
- **`map:` / `sv_map` reaches a game without a GSMapSession** through `start_on_map(id) -> GSResult` (Zombie Zone); a game with neither logs an ERROR, not a warning.
- **On 4 the launcher updates itself and runs again, once** (`self_update` / `update_and_restart` in `tools/server.in`): fetch this checkout's branch and reset to it, `setup.sh --no-games --update`, then `exec ./server` with the original arguments and `TMC_AUTO_UPDATED=1` so a lock that still cannot run the game does not loop.
- **`TMC_AUTO_UPDATE` / `--auto-update`** (the egg's "Update addons automatically"): `when-needed` (default) also updates on start when what the channel follows has moved (`lock_moved`: one shallow fetch): **any new commit of the host itself**, or the lock or `web/shell-build` (before 2026-10-15 a shell pinned without a lock bump reached no box; before 2026-10-25 a fix under `host/` that changed neither reached no box on restart); `always` updates every start; `never` does not.
- **`TMC_CHANNEL` / `--channel`** (the egg's "Update channel"): `latest` (default, what every box did before the setting) follows the branch head; `stable` (also written `@stable`) follows the newest `v*` tag of the host (`sort -V`), reset onto the tag with the branch name kept, and the addons follow that tag's `addons.lock`, whose entries are release tags. Commits after the newest tag are not a move on `stable`; a box with no release tag stays where it is. The pinned-shell gate applies to both. It is read by the launcher, so **a box installed before 2026-10-25 needs one reinstall** to get both this and the host-commit trigger: its old `./server` has neither. Checked by `tools/check_channels.sh`.
- It resets only a deployment (a shallow clone, or a checkout whose HEAD origin already contains), and needs `git` in the runtime. **Local changes no longer stop it**: file modes are ignored (`core.fileMode false`), the built-in `content/` descriptors the panel installer prunes are put back, and any other edit to a tracked file is set aside with `git stash` and listed in the log. The same goes for the addon clones under `addons/.repos/` on `setup.sh --update`, where untracked files never count. Before 2026-10-14 a dirty checkout made every panel box refuse its own update, silently, so no box moved past the addons it was installed with ([history](history.md)). Any remaining reason not to (no git, a developer's own commits, no network) means "start on what you have" and is printed.

## `sv_web_build`, `sv_web_requires` and `web/shell-build`

**A server uses the site's newest compatible shell by default, and moves to a new one with no update and no restart.** `sv_web_build` is a NOTIFY cvar registered on every server and EMPTY unless the operator pins a build: the pin is a decision (a server deliberately held on an older shell), so it comes from the layered config like `sv_web_loader`: `sv_web_build` in `cfg/server/server.yml`, `--web-build`, `TMC_WEB_BUILD` (the egg's "Web shell build (pin)"), or `sv_web_build <id>` over rcon. It is a config field (`TmcConfig.web_build`), not a console line ([configuration.md](configuration.md#the-configuration-is-a-surface-not-a-second-parser)). A value that is not one path segment is warned about and reported empty. `./server check` asserts the cvar is NOTIFY and equals the configured pin.

- **Why it changed**: the cvar used to report the tracked `web/shell-build` for every server, so a server pinned whatever shell its checkout shipped and needed an update plus a restart to move, while the site had already published a newer one.
- **`sv_web_requires`** is the other half: a NOTIFY cvar holding compact JSON of the addon API levels the loaded game's pack needs (`{"gs_net":3}`, the highest per addon over the game's pack and its dependencies, read from each mounted pack's `requires.json`, gs-cloud [mounting.md](../../gs-cloud/docs/mounting.md)). Empty when the pack has none. The host republishes it each time a game loads. The site picks the newest ACTIVE shell whose API levels satisfy it.
- **`sv_pack_pins`** is a NOTIFY cvar holding compact JSON of `{content id: version}` for every pack this server is pinned to: the addons its `addons.lock` names (`modcommunity/gs-*`, and the same version under its new `gamespice-platform/<name>` id, only while `TMC_ADDONS_LOCK` is not `off`) and each pack mounted from the site (maps, the game, dependencies). The host sets it (`TmcHost.pack_pins_json`) and republishes as packs mount; empty when nothing is pinned. The site's content-retention sweep reads it (website-city `ServerPinnedVersions`) so a retention policy never tombstones a map or addon version a server runs.
- **The site honours a pin only for a build it has a row for** (website-city `WebGameBuild`, Admin → Game) that is ACTIVE or DEPRECATED; a DISABLED or unknown pin falls back to the automatic choice. The admin panel lists pins with no row under "Pins being ignored".
- **`web/shell-build` is only the checkout's record** of the shell exported from its `addons.lock`; the web-shell release workflow still writes it, and auto-update still waits for it to be pinned before adopting a new lock. No server reads it as a pin. `web/shell-build.inputs` says which tree it was exported from: `lock` (sha256 of `addons.lock`) and `inputs` (sha256 over the lock, the tracked `client/`, `project.godot`, `export_presets.example.cfg`, `web/embed.html` and the engine pin; `tools/shell-inputs.sh paths`).
- **How a build is registered**: the site's `web-build-register` job (every minute) registers a build from `game/<app>/latest.json` (written by `publish-web-shell.sh --pin`) or one a server reports as `sv_web_build`, once its entry answers on the content origin. A shell is therefore registered within a minute of publishing, with no server involved.
- **The shell's API levels** are written by `export-web` into the build as `shell-api.json` (`{"gs_net":{"level":3,"oldest":1},...}`), which the site reads at registration to answer "does this shell satisfy this game".
- **The site caches the release list for 60 s**: after changing a build's status or a server's pin, wait a minute before testing what a launch resolves.

### Proving it on the dev site (games.tmcdev.net)

The route that was run end to end on 2026-10-31; everything here is dev only.

1. **A shell with its API**: `heavy -- tools/dev-shell.sh --backbone https://games.tmcdev.net`. It regenerates a stale `./server` (an old one exports no `shell-api.json`), and `dev-shell-publish.sh` registers the row with `api` filled from `web/build/shell-api.json`. Since 2026-11-11 the upload goes through the dev site's web build API (`publish-web-shell.sh --api https://tmcdev.net`, which writes to storez), so `~/godot/.env.dev` needs the dev site's `SHELL_PUBLISH_TOKEN`; the S3 bucket and the `/srv/tmc-game` install are no longer used.
2. **The loader**: the dev site's shared loader must be the current `web/tmc-loader.js`, or Play solo opens the connect form (only its `soloParams()` passes `?solo=` to the shell). POST it as in "The shared loader publishes itself" below, with a dev key from the dev site's Admin → Game; the launch answer's `loaderUrl` then names `loaders/git-<sha>`.
3. **Solo**: website-city's `prisma/seeds/dev-games.ts` (`seedSolo`) gives app 101 a `contentAssetId` and `directPlay`. Play solo on `/arena` frames the newest ACTIVE shell with "Playing solo, with no server" and it starts the game pack (`solo game started`): on a GPU box's Chrome the 0844 shell played `gamemann/game-fatal-contact@0.1.33` against bots. A headless browser under `heavy`'s 1 GB cap runs out of memory before the game starts, so do this on a GPU box.
4. **The pin**: a server's `sv_web_build` reaches the site as a `ServerVar` row. The dev site has no worker, so set the row by hand. Then `POST /api/app/v1/play/launch {"appId":N,"mode":"web","serverId":S}` answers `boot.game.build`: the pin for an ACTIVE or DEPRECATED row, the newest ACTIVE for a DISABLED pin or none.
5. **A creator's pack on a server**: publish with `gs-cloud/tools/publish_pack.sh --site https://games.tmcdev.net --id <repo> --meta entry=entry.tscn --meta side=both` and a `licence.json` at the source root. A creator's first release is HELD until approved. List it under `defaults: add:` in the server's `cfg/content/addons.yml` and restart. The console then says `an extra pack started`, and a browser that joins logs the same line with `side=client`: an extra pack's entry is started by `TmcAddonEntry` from its signed manifest, whatever its owner (`ADDON_NAMESPACES` gates only overlays that replace the build's addons, see [addon-packs.md](addon-packs.md#whose-packs-may-replace-the-builds-addons)). Both the unpinned and the pinned shell joined game-playlot this way and showed the creator pack's label in game. A scripted browser join needs a GPU box: `tmcdev.net` resolves to a private address, so Chrome blocks the WebSocket from the public `dev.dotgames.org` page (`ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`) and refuses the dev CA. Start Chrome there with `--ignore-certificate-errors --disable-features=LocalNetworkAccessChecks,LocalNetworkAccessChecksWebSockets,BlockInsecurePrivateNetworkRequests` and a `--remote-debugging-port`, tunnel the port, and drive it with Playwright's `connectOverCDP`.

## `sv_web_loader`

Names a version of the site's shared web game loader (the JavaScript that frames the shell). The site serves the newest active loader by default; a server reporting `sv_web_loader <version>` gets that one while it is not disabled. It can hold a server back but never turn a launch into an error.

- **It is the operator's decision**, like `sv_web_build`, so it comes from the layered config: `sv_web_loader` in `cfg/server/server.yml`, `--web-loader`, `TMC_WEB_LOADER`. It is a config field (`TmcConfig.web_loader`), not a console line ([configuration.md](configuration.md#the-configuration-is-a-surface-not-a-second-parser)).
- `TmcHost._register_web_loader` always registers the NOTIFY cvar, empty unless configured, so it can be set over rcon. A value that is not one path segment is warned about and reported empty. `./server check` asserts it.
- **The desktop client has no equivalent yet**: it installs one build per platform, so a server ahead of or behind it is refused at signon.

## Main is free, releases are batched

- **A push to `main` runs CI and nothing else.** `web-shell.yml` and `native-shell.yml` have no push trigger; no push creates a `v*` tag or touches the prod bucket.
- **The dev channel** (`tools/dev-channel.sh`, from cron on the box that hosts the LAN dev CDN: `*/5 * * * * tools/dev-channel.sh --async`): builds the shell of `origin/main` (`--ref` takes a dev tag) and publishes it to the dev CDN through `tools/dev-shell.sh`. It rebuilds only when the `tools/shell-inputs.sh` fingerprint changed, runs detached, fails loudly (exit 1, `FAILED` in its state dir, `--status`), never tags, never writes the prod bucket and is not prod-gated. It is a poller, not a workflow, because GitHub runners cannot reach the LAN. Tested offline by `tools/check_dev_channel.sh`.
- **The prod release is one command**, run by whoever releases, a few times a day at most: `tools/release.sh`. It takes `origin/main`'s head as the candidate, runs `tools/release_smoke.sh` (on staging02 through `gpu.sh cdp-run`: each of the 14 games in `tools/release_games.txt` in a COOP/COEP parent against the real prod manifests, canvas polled, no console error, sync failed=0, a second launch downloads nothing), records the verdict as a git note `refs/notes/release-smoke` on that SHA and pushes it, then runs `tools/publish_gate.sh --prod <sha>`, and prints the next steps: `gh workflow run web-shell.yml -f candidate=<sha>` (and `native-shell.yml`), then the `v*` tag.
- **What the smoke counts as a failure.** It prints `waiting for a GPU box` while `gpu.sh cdp-run` queues (up to `GPU_CDP_WAIT`, default 1800 s) and a progress line every 30 s while a game loads. A game FAILS on: no canvas, no `solo game started`, a manifest that did not download, `sync finished ... failed>0`, a console `[error]` or `[pageerror]` (other than a network line), a second launch that downloads anything, and `THREADS UNAVAILABLE` (the smoke frame is always COOP/COEP, so threads must work). An HTTP 404, 429 or 5xx on a fetch (for example a missing `zee-gs-weapons/latest.json`, or a 429 under load) and a canvas other than 1280x720 are WARNs listed by path: the game still ran. A 404 becomes a FAIL only when the game itself logs an error naming that file.
- **The prod gate has no override.** `publish_gate.sh --prod` refuses when the repo's CI or Release run for the commit is not green, check-pins fails, the shell stamp is `-dirty`, gs-cloud's CI on main is red, or the smoke note for that exact SHA is missing or not `PASS`. `release.yml` runs it again as `--prod-tag` on the tag (a shell-pin commit is walked back to the candidate it pins). `tools/check_publish_gate.sh` covers every refusal.

## Publishing the web build

**The web-shell workflow does it** (`.github/workflows/web-shell.yml`), started by `workflow_dispatch` with a `candidate` (main's head) after [the release command](#main-is-free-releases-are-batched), never by a push. Nobody exports, uploads, pins or registers a shell by hand:

1. A dispatch (formerly: a push to `main` that touched a shell input; the inputs are (`addons.lock`, `client/`, `project.godot`, the presets, `web/embed.html`, the engine pin) starts it. It checks out `main` and compares `tools/shell-inputs.sh print` with `web/shell-build.inputs`; equal means the pinned shell is this tree's and it stops.
2. Otherwise: `./setup.sh --no-games` (fresh addon clones at the lock, so `tools/addons-lock.sh check` passes), `client/auth.json` from the `WEB_SHELL_BACKBONE_URL` variable, `./server export-web --zip`. The export writes `shell-inputs.txt` into the build: the fingerprint, plus `addons off-lock` when the linked addons are not at the lock.
3. `tools/publish-web-shell.sh --pin` uploads it to `game/<app>/<build id>/` in the bucket (brotli, one content type per file, immutable), reads the entry and `shell-inputs.txt` back through `WEB_SHELL_ORIGIN`, writes `web/shell-build` and `web/shell-build.inputs`, commits "Pin the web shell <id>", tags the next `v0.1.x` and pushes both in one atomic push (rejected because somebody pushed meanwhile: it replays the pin on origin and retries with the next tag, unless origin changed a shell input, when it stops and that push's run builds). It refuses a build whose record is off-lock or is not this checkout's (a lock pulled between export and pin).
4. It dispatches `release.yml` on that tag (and a later run that finds a matching record but no `v*` tag at or after the pin commit tags main and dispatches it, so a pin is never left unreleased), because a push made with the workflow's own token starts no workflow. The pin commit touches no input, so nothing loops; runs queue one deep and the next one finds the record matching.
5. Servers on `TMC_AUTO_UPDATE=when-needed` move on their next start, and the site registers the build itself (below): from `game/<app>/latest.json`, or when the first server reports it.

**A shell no server runs is registered from a pointer.** With `--pin`, after the upload is read back, `publish-web-shell.sh` writes `game/<app>/latest.json` (`{build, entry, notes, lock}`; `lock` is the sha256 of the build's `shell-inputs.txt`; short cache, same bucket and credentials) and the site's `web-build-register` job reads it every minute: when `build` is newer than the app's newest registered build, matches the publish timestamp shape and its entry answers on the origin, it writes the `WebGameBuild` row (notes say `manifest`), so solo play stops serving the previous shell. A malformed pointer is logged and ignored; the server-reported path is unchanged. `--manifest-only` prints the pointer; `tools/check_publish_manifest.sh` tests its shape (part of `tools/check.sh`).

**Without S3**, `--api SITE` uploads through the site's web-build route instead ([web-shell-api.md](web-shell-api.md)).

**The shared loader publishes itself too.** `web/tmc-loader.js` is not part of the shell: the site serves it to every page that frames one. The workflow's `loader` job POSTs it to the site's `/api/app/v1/web/loader` on every run, labelled `git-<12 hex>` after the last commit that touched the file. The site answers a label it already has with the same bytes as "unchanged" (HTTP 200) and writes nothing, so posting on every run is what makes an overtaken run or a manual dispatch unable to lose a loader change; a label it has with different bytes is refused (409). It needs the secret `TMC_LOADER_PUBLISH_KEY`, issued in the site's admin panel (Admin → Game → **Loader publish key**: generate, copy once, `gh secret set TMC_LOADER_PUBLISH_KEY --repo gamespice-platform/server-deploy`). That key opens only this endpoint and acts as nobody; rotating it in the panel stops the old one at once. Unset, the job skips with a notice and the loader is uploaded by hand as before ([web/README.md](../web/README.md#letting-the-site-publish-it)). A non-2xx fails the job and prints the site's answer. **Disable a bad version in the panel rather than deleting it**: deleting frees its label, and the next run publishes the same bytes again.

**What it needs** (repository settings → Secrets and variables → Actions): secret `SHELL_PUBLISH_TOKEN` (the site's shell publish token; the workflow publishes through `--api`, no S3 keys); variables `WEB_SHELL_BACKBONE_URL` (what `client/auth.json` names; the first-party server list is not a variable, the shell asks the site) and optionally `WEB_SHELL_API` (default `https://moddingcommunity.com`), `WEB_SHELL_ORIGIN` (the content origin whose `/<app>/<build>/` is `game/<app>/<build>/`, in prod `https://content.gamespice.net`; when set, the upload is read back before the pin) and `WEB_SHELL_APP` (default `godot`). For the loader job: secret `TMC_LOADER_PUBLISH_KEY` and optionally the variable `TMC_SITE_URL` (the site to publish to, default `WEB_SHELL_BACKBONE_URL`); both are optional and skip with a notice. Workflow permissions must allow `GITHUB_TOKEN` to write, and nothing may block it from pushing to `main` or creating `v*` tags. `GS_DEPS_TOKEN` is used for the addon clones when set. A missing setting fails the run by name before anything is built. `workflow_dispatch` with `force` re-exports when the record matches (a new backbone URL, a broken upload).

**No release goes out with a shell that is not its own.** `release.yml`'s `shell-pin` job refuses a tag whose tree does not match `web/shell-build.inputs`, and, with `WEB_SHELL_ORIGIN` set, whose build on the origin carries a different record. gs-ci's `server-compat.sh`, which every game release runs against the newest gs-server-deploy tag, skips a tag whose recorded lock hash is not its lock's, so a game can only be released against a lock whose shell is live. And `./server`'s auto-update does not adopt a lock pushed on the branch until its shell is pinned (`lock_moved`), so a box never serves new addons to players framed in the old shell. **Do not tag a lock bump by hand**; push it and release the workflow's tag.

**By hand, the fallback** (the workflow is down, or a box that is not CI). **It needs a checkout whose addons are exactly at the lock**: a developer box's `addons/` links sibling checkouts, usually ahead of their tags, and `export-web` marks such a build off-lock, which `--pin` refuses. Use a separate clone set up with `./setup.sh --no-games` (its own clones, at the lock), or check every sibling out at its locked tag. Then: `tools/addons-lock.sh check` (must pass), `./server export-web --zip`, then `tools/publish-web-shell.sh --zip web/build.zip --pin --app godot --origin https://content.gamespice.net --env <file with GAMES_S3_*>`. **The prod content origin is `https://content.gamespice.net`** (it serves `game/<app>/<build>/` as `/<app>/<build>/`); `dotgames.org` answers 404 since the move to storez (checked 2026-11-17), so `--origin https://dotgames.org` fails every read-back. On the developer box `~/godot/deploy-web-shell.sh` is a wrapper that runs this with the `.env` beside it; give it `--origin https://content.gamespice.net` too. `--dry-run` uploads nothing, `--no-push` commits and tags without pushing. `--wait-registered [SEC]` then polls read-only until the origin serves the build (and, with `SHELL_REGISTERED_URL`, a page lists it), exiting 1 with what is missing. The site registers a build itself (the `web-build-register` cron job, every minute) from a game server's `sv_web_build` or, for a `--pin` publish, from `latest.json`, so a pinned shell goes live within a minute or two without a server.

`./server export-web` writes `web/build/` and **publishes nothing**. An export that was never published is indistinguishable from a fix that did not work, because the browser runs the previous build and prints the previous errors byte for byte. There are three deployment shapes and they publish differently; [web/README.md](../web/README.md) opens with the table and a ten-second check for which shape you are on. Check the deployed bytes before believing any conclusion about client behaviour.

**`export-web` refuses to finish if any imported map's `.bin` geometry is missing from the pack.** The Web preset exports `all_resources`, which carries the `.json` manifest (Godot has a JSON loader) and not the `.bin` (nothing loads it); `include_filter` is the only thing that carries it. The bash and PowerShell launchers share one check.

**The presets exclude `cfg/*` on purpose, and that also drops `cfg/addons/**`.** Godot 4.7.2 lets `exclude_filter` win over `include_filter`, and `*` matches `/`, so the `include_filter` entry `cfg/addons/*` ships nothing here. That is the decision: the shell is not a game and has no `cfg/addons/` of its own (`cfg/` holds the operator's secrets, `rcon.yml` and `auth.yml`, and narrowing the exclude would risk shipping one), so the exclude stays whole. Games ship their own addon defaults in their own exports. The `gs-ci` filter check prints a WARN (not a failure) for this exclude, which is expected here.

## Native addon libraries

An addon with a native library (gs-sim, `docs/native-ci.md` there) releases the same way: tag it. Its release workflow attaches `<addon>-<version>-<platform>.zip` per desktop platform plus `natives.json` and `SHA256SUMS.natives` beside the GDScript zip. The site still publishes the pack from the release and signs it; **the library is never in the mounted pack** (a GDExtension must be a file on disk). `setup.sh` (step "native libraries") and `export-native` (for the platforms being built) run `tools/fetch-natives.sh`, which lifts gs-bootstrap's `fetch_natives` (sha256-checked against `SHA256SUMS.natives`, stamped, a library built locally is kept) and unpacks the platform zip of the tag `addons.lock` pins into the gs-sim repository the addon links to, logging `gs-sim: native motor=on`. `GS_NATIVES=none` skips it. Windows does the same through `tools/fetch-natives.ps1` (`setup.ps1`, `server.ps1 export-native`), which lifts `Fetch-Natives` out of gs-bootstrap's `bootstrap.ps1` by parsing it. Both keep a stamp per platform (`bin/.natives-<platform>`), because gs-bootstrap has one per folder and `macos-arm64` plus `macos-x86_64` in one run would otherwise undo each other and re-download every time (the same fix belongs upstream in gs-bootstrap). **`export-web` ships it as a side module** (gs-sim v0.2.6 on): it runs `tools/fetch-natives.sh --platform web-wasm32`, and the Web preset exports with Godot's dlink nothreads template (`variant/extensions_support=true`, `*.gdextension` kept, `addons/*/bin/*` still excluded, since Godot copies the library itself). The build then carries `index.side.wasm` (the engine, which `publish-web-shell.sh` puts beside the shared `index.wasm`) and `gs_sim.wasm` beside the page, which `embed.html` loads from the stamped `gdextensionLibs`. `?natives=0` on the page starts without it, and a page whose side module fails to load retries once that way, so a player always gets the GDScript twins at worst. `TMC_WEB_NATIVE=0`, or no web zip for the pinned tag, exports the old way (plain template, `*.gdextension` excluded, `export-web` refuses a pck that carries one); `export-web` rewrites the box's Web preset to match either way. Non-gs addons (godot-sqlite) stay excluded. The Windows `server.ps1 export-web` builds the script-only client. gs-sim's `docs/web.md` has the browser measurements. A platform without a zip runs GDScript too, so a missing native build is slower, never broken.

A library that arrives under `setup.sh --no-import` (the egg, the container entrypoint) still forces an import, because Godot loads a GDExtension only once `.godot/extension_list.cfg` lists it. The container build fails when the image has no Linux library (`--build-arg GS_NATIVES=none` builds without). The server and the shell log `gs-sim native: bots=yes motor=yes snapshot=yes` at startup (`TmcNativeStatus`), and `tools/check.sh`'s parse pass ignores godot-rust's `Initialize godot-rust` banner, which a loaded library prints on every run.
